## Decision and boundaries

Issue the first admin credential through the hosted OAuth consent service. Use a distinct **admin grant class** with separate consent, resource, scope set, provider grant, refresh family, and connection identity. On the OAuth wire, retain the standard `authorization_code` and `refresh_token` grant types; “admin grant type” means this separate authority class, not a new client-facing mint or nonstandard `grant_type`. No existing MCP consent implicitly authorizes admin access.

The only admin credentials after cutover are OAuth-issued ES256 access JWTs and the provider's rotating opaque refresh tokens. Delivery is the normal HTTPS OAuth token response to the MCP client's credential store. Retire `handleAdminRuntimeCommand`, its runtime-proof actor, `swm_adm_`/`swm_adr_` issuance and validation, and its private admin delivery callback. Reuse its bounded pinned-issuer/JWKS verification primitives for verifying the OAuth access JWT, with the new claims and DPoP checks below. A signed OAuth access JWT authorizes routine commands directly; it cannot authorize another mint through the old proof route.

**Hard activation gate:** proposed `admin_issuance_enabled` defaults false and must stay false through lanes 3–4 until lane 5 has landed and its legacy-unreachable test passes. Both authorization and `/token`, including refresh, enforce it; `getResourceServerInfo` must reject the admin resource while closed. A consent-page flag alone is insufficient. Activation additionally requires a durable cutover marker written only after legacy rows are terminally fenced, exact reviewed live lane-5 revision/readback, and the lane-8 complete-chain proof. Missing configuration, marker, revision or proof fails closed. Neither an enabled flag with an old edge nor a new AS with an old opaque credential path may issue admin tokens. Closing issuance later does not replace revocation of existing grants.

Make that predicate executable: M3 `admin_cutover_state` records terminal `legacy_closed`, the approved lane-5 release identity/auth-contract version, required migration IDs/checksums and lane-8 evidence digest. Only the reviewed release role may write it; AS/edge roles cannot supply or change release measurements. The activation gate reads **both** (a) the live edge release measured by the release worker on the box and (b) the database's migration ledger together with D2 `commonswarm_ops.migration_checksums`, comparing **version + sha256** for all five admin prerequisites (`20261001000001..05`), the OAuth store (`20260928000003`), DCR (`20261002000001`) and M1–M3 against the reviewed release inputs. The checksum table is release-owned and only the release role may write it; each checksum is written in the same transaction as its migration-ledger insert. In the next schema window, backfill already-applied migrations from repository files at the SHA that was released and explicitly mark those checksum records as backfill. AS/edge/runtime roles cannot write checksums; a migration version alone is insufficient. A configured SHA or edge-process report is insufficient. In the same marked edge release step that switches the release, the worker resolves `/home/commonswarm/edge/current` to the immutable reviewed release directory, verifies its artifact checksum and the running container's image digest/mount against that release, and writes the measured target, digest, release generation, measurement time and worker/step evidence reference into the release-role-owned record. The AS compares this operator measurement with the approved release identity, not a value reported by the edge process. `/admin/.well-known/readiness` may remain diagnostic only; its SHA/status never grants trust, substitutes for either input or opens the gate.

**Re-check cadence:** the worker remeasures before final activation and during every edge release switch, recreation or rollback, in that same release step. Close issuance and invalidate the measurement before changing the edge; it remains closed until fresh measurement and ledger readback succeed. All authorized release paths must enforce this sequence, so a prior receipt cannot authorize a changed deployment. Before **each** admin authorization, consent completion, resumed code issuance and code/refresh exchange, the AS rereads the current measured-release record, live migration ledger and D2 checksum table along with flag, closure marker and lane-8 proof; no cached positive gate. `getResourceServerInfo` invokes the same predicate. Missing/invalidated measurement, wrong target/digest/generation, incomplete/mismatched ledger, unavailable lookup or absent closure/evidence refuses. Release rollback also leaves opaque database access permanently fenced. Lane-4 `admin-activation-measured-release` and `admin-activation-migration-ledger`, required by lane-8 `admin-activation-chain`, pair a correct measured-release/complete-ledger positive with old edge reporting the approved readiness SHA, altered target/image, invalidated receipt, missing migration and checksum mismatch negatives. A lying readiness endpoint cannot make any negative pass.

DPoP is mandatory for **every admin scope, including read-only**. Clients unable to retain a DPoP key and produce proofs cannot request admin grants. They may continue using the ordinary MCP connector. This is a release compatibility gate, not a reason to fall back to bearer admin tokens. The admin connector is a separate MCP resource at `https://api.commonswarm.com/admin`; ordinary coordination remains at `https://mcp.commonswarm.com/mcp`.

Consent explains an incompatible client before offering permissions: “This client cannot prove possession of its access key. Admin access is unavailable. You can use the ordinary MCP connection.” It cannot confirm an admin receipt. Provider DPoP algorithm advertisement or default enablement does not establish this requirement; lane 4 explicitly requires proof/key binding at code exchange and refresh, and lane 5 requires it at every protected request.

The first release defaults to thirty days and permits an earlier positive expiry, with a thirty-day maximum. Only fresh human consent creates a replacement grant and new family. Refresh does not renew the grant or extend its absolute deadline. Full account remains bounded routine administration, with no implicit permission to create further admin grants.

This specification does not implement billing, unsupported routine operations, external provider authorizations, human impersonation, or a CLI issuance verb. Provisioned worker credentials remain a separate credential class. Their existing protected recipient delivery is not a second admin authentication system and must never be presented as the way to issue the first admin credential.

## Consent and authority mapping

The client requests a maximum scope envelope; the person can choose an equal or narrower subset. Render both the client's request and the final human selection from one versioned registry shared with enforcement. Never add a scope the client did not request. Full account is available only when the request permits the complete supported routine bundle. No wildcard OAuth scope and no silent conversion of broad granular choices into full account.

Start in “Choose permissions” mode, with read-only selected and all mutation boxes clear. Offer “Full account” as a distinct radio choice, followed by a second confirmation of the complete summary. Read-only can be used alone or accompanies each mutation group. The following maps to the existing registry at `src/protocol/admin-policy.ts:22`; the copy and availability proposed here are requirements, not current UI claims.

### Registry and dormant-permission fencing

Registry-v1 validation requires every scope, including unavailable operations (`src/protocol/admin-policy.ts:108`). Do not issue new OAuth admin grants with that shape. Lane 1 proposes a canonical manifest revision, allocated as registry v2 before issuance, adding sorted, unique `capability_names` (exact command names) and an immutable `availability_digest` alongside `registry_version` and `scope_names`. Include all in `manifest_digest`, the consent receipt, grant projection and provider binding. Full account explicitly selects the complete **available routine** bundle at that version, within the client's requested ceiling; granular selects its subset. Unsupported scopes and commands are disabled in consent and absent from both lists. OAuth consent MUST NOT call the registry-v1 validator; only the revised v2 validator may admit its manifest. Old v1 rows/digests remain historical and terminally fenced at cutover; they are never converted or inferred as OAuth consent.

One shared, versioned availability map, keyed by registry version and command, supplies consent rendering, `adminManifestValid`/effective policy in `src/protocol/admin-policy.ts`, `parseAdminRoutineCommand` in `src/protocol/admin-routine.ts`, and admin tool listing/dispatch. The parser refuses an unavailable command before any effect even if the scope exists. Dispatch intersects the consented version's command definitions/capability list with current executable availability from that same map; scope presence alone is insufficient. A current removal immediately restricts use without rewriting the immutable consent snapshot. Adding a scope, adding parser support, or changing a command's authority semantics requires a registry version increment and new consent; changed authority definitions cannot execute under older consent. Missing/unknown versions refuse, never fall back to the newest map. Even an accidental same-version availability addition cannot expand an old explicit capability list. A new command sharing an old scope still fails this test. Lane 1 must prove both cases with old/full and new/fresh-consent controls. This work does not implement the unavailable routine commands.

Require a fresh trusted human authentication (within five minutes), verified Origin, CSRF token, and single-use consent receipt bound to the session and canonical exact manifest. Bind request client ID, redirect URI, resource, PKCE challenge, DPoP key thumbprint, metadata snapshot, scope ceiling, interaction/version, and replacement grant as well. Changed inputs invalidate confirmation. Back/refresh can recover a pending request but cannot confirm twice or substitute a broader manifest. A model acknowledgement or an operator approval flag is not human consent. The current core already checks session-bound, unconsumed, unexpired receipts and explicit full-account selection (`src/protocol/admin-authority.ts:174`, `:185`; `supabase/functions/command/admin-delegation.ts:358`); the extra OAuth bindings are new work.

### Client identity and phishing rules

All admin clients require an active service-owned **verification record** (client metadata pinning; HezLead may prepare evidence) and a separate **one-time account-owner approval in `/app`** for that exact client and verification version, before hosted admin consent. Use **account owner** for the human who owns the account (`owner_user_id` / `ctx.owner_user_id`). That principal is distinct from **`ctx.withdrawing_workspace_owner`**, the workspace-scoped actor checked by `withdraw_admin_workspace_access` (`src/protocol/admin-authority.ts:220`–`:221`): a workspace owner who withdraws access from a shared grant is not the account owner and cannot approve admin clients.

Owner approval is **scoped per account**, not a global client row. The durable key is `(owner_user_id, client_id, verification_version)`; one account owner's approval never satisfies another account's consent even for the same client identity. Absent matching approval for the consenting account refuses, including zero-workspace setup. Reuse of that approval does not replace fresh human consent for each grant/renewal.

Owner approval is written **only** through new human-only account commands `approve_admin_client` and `withdraw_admin_client_approval` on the same transactional command path as `grant_admin_delegation`, with the same actor rule: `actor.kind === 'human' && actor.user_id === ctx.owner_user_id` (`src/protocol/admin-authority.ts:166`–`:187`). Refuse `worker`, `hosted_seat`, `delegated_admin`, agent tokens and any non-human actor. No `SECURITY DEFINER`, OAuth-schema privileged write, verification-prep side path or metadata callback may stamp or imply owner approval; the verification record can be inserted or updated only by reviewed operator roles and **never creates approval**.

At hosted admin consent and every AS edge authority check, require: consenting session user equals the approving account owner for the same `(client_id, verification_version)`; verification active; versions match. List the client, approving account owner and approval/version with each grant in `/app`.

Verification records pin canonical `client_id`, exact redirect URI set, application type, publisher identity and independently checked publisher contact, canonical metadata digest/version, allowed admin scopes and separate full-account eligibility; delegation is ineligible in v1. Store nonsecret review evidence references and successful PKCE/DPoP/redirect test results in the verification row only. Verify publisher control of the metadata origin using an independently established contact and an origin-control challenge; inspect redirects, proof-key storage and the consent/code-exchange flow. This is a human-reviewed trust decision, not cryptographic client authentication or a promise of safe future behavior. Do not seed an assumed reviewer client; no verification record means no admin access.

CIMD hosting alone grants no eligibility. Ordinary-MCP RFC 7591 DCR stays enabled (`features.registration.enabled=true`), live since 2026-10-02 per [DCR release evidence](../evidence/2026-10-02-dcr-release/RELEASE-V2.md). The v1 admin consent policy refuses any client whose provenance is DCR for the admin resource, independent of verification or owner-approval rows. Native applications, loopback redirects (including `localhost`, IPv4/IPv6 loopback) and custom URI schemes are refused for admin in v1, even with a verification/owner-approval record. **No native/loopback exception.** Every admin client must use hosted HTTPS consent with mandatory PKCE S256, authorization-code `dpop_jkt`, same-key exchange/refresh and protected key storage. `nativeLoopbackEnabled` for ordinary MCP confers no admin eligibility; no generic loopback wildcard. Unverified clients cannot see the full-account option or delegation; verification is also enforced server-side for granular consent. Unknown CIMD clients may use ordinary MCP; admin returns `unauthorized_client` with a safe reason.

Display escaped text only; do not fetch remote client logos on consent. Preserve pinned public-HTTPS metadata fetching, body/time bounds and redirect refusal (`services/mcp-auth/src/metadata-fetch.js:234`, `:300`). A metadata digest, redirect, application-type or publisher/contact change invalidates every scoped owner-approval row for that client/version and immediately marks verification ineligible and fences existing admin grants/families in the same lifecycle transaction; fresh reviewed verification, explicit account-owner reapproval through `approve_admin_client` and fresh consent are required, never automatic reactivation. Check the approved snapshot at authorization, consent finish, code exchange and refresh, and active verification plus matching account-owner approval/version in every edge authority transaction. The account owner withdraws approval only through `withdraw_admin_client_approval`; operator verification withdrawal is separate. Either withdrawal records a reason and atomically suspends/revokes linked grants and tombstones their families for that owner/client binding. If metadata cannot be checked at authorization/token processing, refuse rather than trust an expired cache. Lane 3 tests changed metadata, scoped approval withdrawal and re-verification without resurrection.

Full account requires a second CSRF-protected, single-use confirmation tied to the exact summary digest and verification snapshot, distinct from selecting its radio button. Warning: “This client can create workspaces and change seats and invitations within these limits. That includes future workspaces you own. Workers it creates may read workspace messages and files. If the client or agent host is compromised, someone else can use this access until it expires or you revoke it.” Show exact capabilities, limits, expiry, client/redirect host and excluded permissions. Edited metadata or summary invalidates the second confirmation. Verification reduces impersonation; a verified malicious publisher remains a residual risk.

## OAuth and resource API

Use issuer `https://mcp.commonswarm.com`, its existing authorization/token endpoints and pinned JWKS, with an explicit resource allowlist. Requests must contain exactly one resource at authorization, code exchange and refresh. Accept `https://api.commonswarm.com/admin` for the admin class and `https://mcp.commonswarm.com/mcp` for the ordinary class; reject arrays, aliases, trailing-slash variations and missing resources. Never allow a single provider grant or refresh family to cover both. A client using both resources gets two independent consents, connection IDs and stores.

### Single-resource provider grants

Add a durable `provider_grant_resources` binding for **both** classes, primary key `provider_grant_id`, with immutable exact resource, owner, client, connection and grant class. Enforce disjoint hosted/admin links; one provider grant ID cannot appear in both. Every code/access/refresh artifact refers to that binding; adapter upserts validate resource/class and refuse mismatches, including a provider Grant payload whose resource-scope map contains another audience. Backfill existing MCP grants only from verified hosted bindings as MCP; missing/ambiguous rows fail closed. A provider session's previous MCP grant is never evidence of admin consent.

**Interim defense in depth (lane 3, before lane 4):** the ordinary MCP `handleInteraction` explicitly throws/denies any authorization whose resource is `https://api.commonswarm.com/admin`, including an admin resource contained in a multi-resource request, **before `Grant.find`, `addResourceScope`, `addOIDCScope` or hosted activation**. This denial is unconditional and independent of `admin_issuance_enabled` and `getResourceServerInfo`; neither a flag nor permissive resource metadata can bypass it. Lane-3 `mcp-interaction-refuses-admin` invokes the actual MCP interaction handler with flag off/on and stubbed accepting resource metadata, proves no Grant lookup/mutation/hosted activation, and pairs refusal with ordinary MCP consent success. Lane 4 may route admin requests to its distinct transaction-aware handler after all gates pass; the MCP handler's denial remains permanent. Lane 8 requires both the interim denial and the final separate-family proof.

Required service changes:

- `services/mcp-auth/src/interactions.js`, `createInteractionHandler` → returned `handleInteraction`, consent finish (`:389`–`:409`, `:451`–`:454`): dispatch by the validated single resource **before** the MCP handler, Grant lookup or hosted workspace selection/consume. Keep the MCP handler's unconditional admin denial; admin requests go only to the separate admin handler. Admin uses the admin receipt and fresh Grant; retry may `Grant.find` only the same pending admin binding after checking owner/client/resource/class. Never reuse an MCP Grant, add admin resource scopes to it, or call the hosted activation path for admin. MCP retries likewise check MCP binding. Fresh admin consent cannot silently upgrade or merge the session's Grant.
- `services/mcp-auth/src/provider.js`, `createMcpProvider` → `features.resourceIndicators.getResourceServerInfo` (`:100`), `defaultResource`/`useGrantedResource`, `extraTokenClaims` (`:150`): closed gate rejects admin at authorization and token endpoints; opened gate selects exact audience/scopes only after verified-client and bound-class checks. Token claims/status derive from the durable class-specific binding, never from requested `resource` alone. Code and refresh must match their original resource, client, key and class; public-client metadata must explicitly require DPoP for admin. Discovery enablement alone is insufficient.
- `services/mcp-auth/src/server.js`, `startServer` → `clientMetadataAccepted` (`:186`): preserve ordinary MCP metadata validation/cache; return/use admin eligibility only from the active pinned verification record, with explicit DCR/native rules. Because this callback currently receives metadata without a request resource, it must not be the sole resource authorization check: wire the same eligibility service into `getResourceServerInfo`, admin consent finish and token processing. `providerGrantActive` (`:177`) resolves the bound class and uses the current transaction's client for admin status.

Lane-4 `mcp-refresh-never-admin` obtains a real MCP code/refresh family, requests admin at refresh and subsequent consent with that same provider Grant, and attempts adapter multi-resource upsert. Each fails without admin artifacts/audit; ordinary MCP refresh still succeeds and separately confirmed verified admin consent succeeds with a different family/connection. Lane 8 blocks activation until this passes on the exact combined build.

Admin scopes are **resource-only** granted registry strings: never add them to provider-level `scopes` or pass them to `Grant.addOIDCScope`. The admin handler uses `addResourceScope` only on its fresh admin-bound Grant and only for the exact admin resource; in the admin handler, `addOIDCScope` is restricted to OIDC protocol scopes. `admin:delegate` is refused in v1. Lane-4 `admin-scopes-resource-only` proves admin scopes absent from global configuration/OIDC Grant scopes, refused on MCP, and usable only on a separately consented admin resource Grant; lane 8 requires it. `openid`/`offline_access` retain their protocol meaning; `mcp` is refused for an admin resource and admin scopes are refused for the ordinary resource. `offline_access` requests the rotating refresh token; without it access still cannot exceed the same consent deadline. Publish exact supported scopes and protected-resource metadata at the admin resource's discovery path, naming the same issuer. An ID token never authorizes an admin operation.

### Atomic issuance and refresh

**Primary design: shared PostgreSQL transactions, no asynchronous issuance outbox unless the explicit fallback decision below is approved.** Lane 4 first proves a transaction integration spike against pinned oidc-provider 9.12.2; it may not ship atomicity as an assumption. The present `transaction(pool, callback)` opens/releases its own client (`services/mcp-auth/src/postgres-adapter.js:35`–`:47`), `consume` is an independent conditional query (`:66`–`:89`), and `revokeByGrantId`/`upsert` open transactions (`:156`, `:186`). Wrapping only `extraTokenClaims` or calling an edge handler after provider save does not satisfy the design.

At AS request ingress, a trusted admin transaction coordinator identifies the candidate interaction/code/refresh and bound class by read-only lookup, then acquires **one** `pg` client, begins a transaction, locks in the order below and re-reads the candidate. Requested resource cannot relabel an MCP artifact. A Node `AsyncLocalStorage` request context carries that exact client and verified lifecycle capability through the separate admin interaction handler, the provider callback/resumed authorization and admin token processing. All admin adapter methods (`find`, `findByUid`, `findByUserCode`, `consume`, `upsert`, `destroy`, `revokeByGrantId`) and status/consent helpers use the context client; no nested BEGIN/COMMIT, independently acquired pool client, or fallback autocommit is permitted for a bound admin artifact. Encountering admin state without context refuses. The existing MCP adapter behavior may remain outside this context, with single-resource checks in both branches. A transaction assertion/traced backend PID proves actual adapter calls participate; AsyncLocalStorage alone is not proof.

The D1 runtime-to-authority bridge uses one dedicated login role, `commonswarm_admin_issuer`, a **NOINHERIT** member of `commonswarm_oauth_runtime` and `swarm_command`. The coordinator acquires its one `pg` client through that issuer login and uses **`SET LOCAL ROLE` per step inside the one issuance transaction**: OAuth storage steps run as `commonswarm_oauth_runtime`, authority steps as `swarm_command`. Never use connection-level `SET ROLE`. The authority reducer is the **same TypeScript reducer bundle the edge runs**, with narrow PostgreSQL lifecycle functions on that same client, writing account grant/projections, event/audit and provider state in that transaction; B2 (SQL re-implementation of the reducer) is rejected. Refactor generated management/consent bindings to accept the coordinator's client instead of calling a remote edge or acquiring `postgres.js`'s separate pool. The issuer gets only the grants the issuance path needs, enumerated in its migration with `admin-issuer-grants-no-widening`, a test that fails on any widening. The OAuth runtime role retains its separation from general `swarm` mutation and gets no `swarm_command` membership. The issuer credential lives next to the existing management credential and rotates with it. These are trusted internal operations with fresh-human or verified-family provenance, never publicly callable mint functions.

Consent and token processing use distinct request-scoped atomic units; no transaction spans a browser redirect:

Account creation works without workspaces. Buffer any `interactionFinished` response until commit; an incomplete grant cannot authorize the continuation. If the provider creates the authorization code on a later resumed `/authorize` request, that request rechecks the committed receipt/grant under locks, persists the one-time code artifact and its lifecycle audit atomically, then returns the code redirect. Signing and all awaited provider adapter saves occur before commit. Token claims/status hooks read the same client. No token artifact or success audit survives rollback alone.

Wrap the entire admin provider/interaction response path with bounded in-memory buffering of status, headers, redirects and body; suppress `writeHead`/`write`/`end`/stream flush until commit. Commit only after all provider adapter writes and audit succeed; deferred/unawaited writes are forbidden. Other failures roll back the whole issuance unit. Proof admission remains consumed independently, so a retry needs a fresh proof. Neither choice is automatically authorized by spike failure; issuance stays closed until the chosen revision and replacement gates pass. B requires a reviewed change to this section's atomicity promise: a durable issuance request keyed by receipt/code or family/generation/request ID reserves bounded authority and writes an outbox event; a lifecycle worker processes it idempotently with explicit `pending`/`ready`/`failed` states. **`ready` is set only in one commit together with the provider token artifact, the `admin_access_issuances` row and the matching `AdminCredentialIssued`/`AdminCredentialRotated` audit; an audit insert failure leaves the record `pending`, never `ready`.** Pending artifacts never authorize: AS token responses and RS admission require a committed `ready` issuance row and live binding; audit presence is part of the ready predicate, not a separate best-effort follow-up. Rotation does not invalidate an otherwise live prior access JWT merely because its generation precedes the newest one. `admin-access-issuance-required` pairs signed-but-unrecorded, rolled-back and mismatched-row tokens with a matching committed live-token success, across both entry points/list/init/read/action/idempotent delivery. Normal planned key rotation retains trusted old keys only for outstanding bounded token lifetimes; emergency withdrawal fences affected families and requires new consent/key material under an incident plan.

Revocation SLA means zero additional authorized transactions starting after revoke commit. A concurrent action that acquires locks and commits first remains valid history; revoke first prevents it. Reads lock/recheck before snapshotting/audit; queued commands revalidate at execution. Only an already-authorized **in-flight** request may finish delivering its committed result, and its execution/response deadline is bounded by the presenting access token's expiry (at most 300 seconds from issuance). Enforce cancellation/output cutoff at that deadline for streaming/long work. The five-minute token TTL is not a post-revoke cache window; completed side effects or data already sent cannot be retracted. If database/status/audit is unavailable, refuse access/issuance/revoke-success acknowledgement. UI presents unknown outcomes with stable retry IDs and readback.

Suspension, expiry, replacement, replay and client-verification withdrawal fence refresh/access likewise. Replacement ends the prior grant and tombstones its family atomically, preserves its history/budgets, and creates a new consent-bound family. Default deadlines are consent activation time plus thirty days; initial issuance delay never adds time. Expiry enforcement uses database time on every call even if a materializing expiry job has not run. Revocation cascades through admin ancestors and provisioned workers; narrowing/withdrawal intersects descendants rather than deleting ancestry.

D3 operations audit uses the bounded kinds **`init`, `list`, `read`, `action`**, bound to the authenticated grant/family, and records human owner, admin principal and grant for authenticated operations, including refusal, protected-action attempt, surrender and failed transaction recovery. Apply a **per-grant daily cap on rows**, continue counting requests beyond the cap, and **never drop `action` rows**, including beyond the cap. Known valid-but-revoked tokens still attribute audit to the verified bound grant/family before refusal. Unauthenticated failures, including completely invalid/unknown credentials, go to the **shared security rate bucket** with a bounded reason and **no victim binding**; do not attribute them to a claimed owner/grant/family. Audit failure blocks a success response; mutation/domain/audit commit together, and rollback failure auditing uses the existing separate transaction pattern (`supabase/functions/command/index.ts:13207`; `supabase/functions/command/admin-delegation.ts:448`). Keep append-only triggers and least privilege; a privileged database administrator remains a residual tampering risk. Export periodic signed audit digests to independent retained storage as a separately reviewed operational follow-up, not a claimed current safeguard.

## Threat model

Assets: human account authority; OAuth authorization code/access/refresh artifacts and DPoP key; consent manifest; current workspace rights; grant/worker dependency lineage; issuance quotas; immutable action evidence. Trust boundaries: browser↔AS, metadata publisher↔AS, AS↔PostgreSQL authority, agent host↔admin edge, admin edge↔workspace reducer, `/app` human session↔revocation, operator↔audit storage. Client input, model prompts and client names are untrusted.

| Threat / STRIDE | Required mitigation and proving control | Residual risk |
| --- | --- | --- |
| Consent phishing / S, E | Verified-client admin allowlist; prominent canonical CIMD/DCR identity and redirect host; no metadata-supplied verified badge; explicit full-account second confirmation, expiry/coverage/worker exposure warning; fresh session + CSRF + exact manifest receipt. Test forged familiar name/unverified client refusal alongside verified granular consent success. | A person may approve a malicious verified publisher or overlook the warning; verification cannot establish future host behavior. |

## Decisions (2026-10-02, HezLead)

These decisions have standing authorization for this specification; Tom may override them through a reviewed revision. They are settled v1 requirements, not pending approval questions.

1. **Delegation deferred:** no delegation scope, child admin issuance, M4 or optional delegation activation in v1; full account cannot create admin grants.
2. **DPoP REQUIRED:** every admin token/scope, including read-only, requires key-bound proof at AS and RS; incompatible clients retain ordinary MCP only, with no Bearer fallback.
3. **Billing label:** use **“Renew seats”**. Billing remains unavailable and grants no authority.
4. **Verified admin clients:** the **account owner** (not `ctx.withdrawing_workspace_owner`) gives one-time approval in `/app` through `approve_admin_client`, scoped to `(owner_user_id, client_id, verification_version)`; record and list that approval with each grant. No automatic approval and no privileged verification write may imply approval. Changed verification inputs require explicit `approve_admin_client` reapproval; every grant/renewal still requires hosted human consent.
5. **No native/loopback exception:** every admin client goes through hosted HTTPS consent; native/custom-scheme/loopback clients are refused in v1 even if an approval record exists.
6. **D1 = B1, issuer bridge:** one dedicated login role `commonswarm_admin_issuer`, NOINHERIT member of `commonswarm_oauth_runtime` and `swarm_command`; one pg client, `SET LOCAL ROLE` per step inside ONE transaction; the authority reducer is the same TypeScript bundle the edge runs. The issuer role gets only the grants the issuance path needs, enumerated in the migration with a test that fails on any widening. `SET LOCAL ROLE` only inside the issuance transaction, never at connection level. The credential lives next to the existing management credential, same rotation. AS compromise = command-capable; mitigations are DPoP, short TTL, rate buckets and audit. B2 (SQL re-implementation of the reducer) is rejected.
7. **D2 = yes, checksum ledger:** release-owned table `commonswarm_ops.migration_checksums`, written in the same transaction as the ledger insert, release role only. Activation compares version + sha256 for the five admin prerequisites, OAuth store, DCR and M1–M3. Backfill checksums for already-applied migrations in the next schema window from the repository files at the SHA that was released; record that it is a backfill.
8. **D3 = yes, bounded operations audit:** bounded kinds `init`, `list`, `read`, `action` bound to the authenticated grant/family, with a per-grant daily cap on rows; count beyond the cap and never drop action rows. Unauthenticated failures go to the shared security rate bucket with a bounded reason and no victim binding.

Everything stays off main until the lane-5 chain is ready; issuance OFF.

The canonical issuance manifest/registry revision is a lane-1 reviewed implementation input. The actual reviewer client and account-owner approval must be measured before release, not assumed here. If lane 4's provider spike fails, the fallback A/B architecture choice in Atomic issuance and refresh remains an explicit Tom/HezLead decision; standing v1 policy authorization does not waive that stop.

Thirty-day default/maximum, five-minute access, normal OAuth delivery, fresh-consent-only renewal, distinct admin resource and retirement of the legacy admin auth are decisions in this specification. They do not depend on inventing a production caller. Any change to them requires a reviewed revision before implementation/release.
