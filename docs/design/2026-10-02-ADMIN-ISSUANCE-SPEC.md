# Hosted OAuth admin issuance: specification and threat model

Status: design only, 2026-10-02. Option A is the supplied HezLead decision under Tom's authorization. This document proposes implementation requirements; it does not claim issuance, tests, migrations, or releases have happened. Source baseline: `cb15e1ae226544798c8c918a35d990a626109938` (`origin/main` at preparation). All file:line references below refer to that baseline, not future line numbers.

## Decision and boundaries

Issue the first admin credential through the hosted OAuth consent service. Use a distinct **admin grant class** with separate consent, resource, scope set, provider grant, refresh family, and connection identity. On the OAuth wire, retain the standard `authorization_code` and `refresh_token` grant types; “admin grant type” means this separate authority class, not a new client-facing mint or nonstandard `grant_type`. No existing MCP consent implicitly authorizes admin access.

The only admin credentials after cutover are OAuth-issued ES256 access JWTs and the provider's rotating opaque refresh tokens. Delivery is the normal HTTPS OAuth token response to the MCP client's credential store. Retire `handleAdminRuntimeCommand`, its runtime-proof actor, `swm_adm_`/`swm_adr_` issuance and validation, and its private admin delivery callback. Reuse its bounded pinned-issuer/JWKS verification primitives for verifying the OAuth access JWT, with the new claims and DPoP checks below. A signed OAuth access JWT authorizes routine commands directly; it cannot authorize another mint through the old proof route.

DPoP is mandatory for **every admin scope, including read-only**. Clients unable to retain a DPoP key and produce proofs cannot request admin grants. They may continue using the ordinary MCP connector. This is a release compatibility gate, not a reason to fall back to bearer admin tokens. The admin connector is a separate MCP resource at `https://api.commonswarm.com/admin`; ordinary coordination remains at `https://mcp.commonswarm.com/mcp`.

The first release defaults to thirty days and permits an earlier positive expiry, with a thirty-day maximum. Only fresh human consent creates a replacement grant and new family. Refresh does not renew the grant or extend its absolute deadline. Full account remains bounded routine administration, with no implicit permission to create further admin grants.

This specification does not implement billing, unsupported routine operations, external provider authorizations, human impersonation, or a CLI issuance verb. Provisioned worker credentials remain a separate credential class. Their existing protected recipient delivery is not a second admin authentication system and must never be presented as the way to issue the first admin credential.

## Consent and authority mapping

The client requests a maximum scope envelope; the person can choose an equal or narrower subset. Render both the client's request and the final human selection from one versioned registry shared with enforcement. Never add a scope the client did not request. Full account is available only when the request permits the complete supported routine bundle. No wildcard OAuth scope and no silent conversion of broad granular choices into full account.

Start in “Choose permissions” mode, with read-only selected and all mutation boxes clear. Offer “Full account” as a distinct radio choice, followed by a second confirmation of the complete summary. Read-only can be used alone or accompanies each mutation group. ### Client identity and phishing rules

All admin clients must be verified by a service-owned allowlist binding canonical client ID, redirect URI set, publisher, metadata digest/version and allowed admin scopes. CIMD hosting proves where metadata was fetched, not that the publisher is safe. DCR registration, if supported, must not create a verified badge or grant admin eligibility. Unknown CIMD/DCR clients may request ordinary MCP; admin authorization returns `unauthorized_client`, with a safe explanation. Full account and `admin:delegate` additionally require explicit entries permitting those options. Reviewer client is registered by the same rules, never an auth-bypass test mode.

Display escaped text only; do not fetch remote client logos on consent. Preserve pinned public-HTTPS metadata fetching, body/time bounds and redirect refusal (`services/mcp-auth/src/metadata-fetch.js:234`, `:300`). Changed redirects/publisher/metadata invalidate admin eligibility until reviewed; recheck at authorization, token exchange and renewal. Warning for full account: “If this client or agent host is compromised, an attacker can change access across the workspaces listed here.” Show the client host prominently so a familiar supplied name cannot mask another publisher. Verification reduces impersonation; it does not guarantee client honesty.

## OAuth and resource API

Use issuer `https://mcp.commonswarm.com`, its existing authorization/token endpoints and pinned JWKS, with an explicit resource allowlist. Requests must contain exactly one resource at authorization, code exchange and refresh. Accept `https://api.commonswarm.com/admin` for the admin class and `https://mcp.commonswarm.com/mcp` for the ordinary class; reject arrays, aliases, trailing-slash variations and missing resources. Never allow a single provider grant or refresh family to cover both. A client using both resources gets two independent consents, connection IDs and stores.

Admin resource scopes are the granted existing registry strings, optionally `admin:delegate` only after its extension. `openid`/`offline_access` retain their protocol meaning; `mcp` is refused for an admin resource and admin scopes are refused for the ordinary resource. `offline_access` requests the rotating refresh token; without it access still cannot exceed the same consent deadline. Publish exact supported scopes and protected-resource metadata at the admin resource's discovery path, naming the same issuer. An ID token never authorizes an admin operation.

| Admin access JWT field | Required semantics |
| --- | --- |
| Header | `typ=at+jwt`, `alg=ES256`, bounded trusted `kid`; reject token-selected key URLs, embedded access-token keys, critical/ambiguous headers. |
| `iss`, `aud`, `sub` | Exact issuer, scalar exact admin resource audience, authenticated human owner UUID. Owner subject is provenance, never human impersonation; actor class below is delegated admin. |
| `grant_class` | Exact `delegated_admin`, required. |
| `grant_id` | OAuth provider grant identifier, preserving the provider's existing claim semantics; never assume it is the admin UUID. |
| `admin_grant_id`, `admin_identity_id`, `connection_id`, `client_id` | Durable bound account grant UUID, account-level admin principal UUID, named connection UUID and canonical OAuth client. Server derives all from the stored binding. |
| `scope`, `registry_version`, `manifest_digest` | Effective scope subset, pinned approved registry version and current manifest digest. Compare against durable state on every use. |
| `jti`, `iat`, `exp`, optional `nbf` | Unique token ID and integer seconds; `exp=min(iat+300, grant expiry, refresh deadline, ancestor deadlines)`. No grace beyond durable expiry; clock skew cannot extend the grant. |
| `cnf.jkt` | Required DPoP public-key thumbprint matching the consent and family binding. |

Return `access_token`, `token_type=DPoP`, actual clipped `expires_in`, exact granted `scope`, and rotating `refresh_token` when requested. Optional nonsecret response metadata includes `admin_grant_id`, `connection_id` and absolute `grant_expires_at`. Set no-store headers. Tokens go only to the OAuth client/runtime credential store, never a model tool result, transcript, URL, redirect fragment, audit, event or report. The authorization redirect carries only the standard short-lived code/state; the token endpoint consumes code plus PKCE and a proof from the bound key.

DPoP binds tokens to a client key; the proof covers method/URI, and resource proofs bind the access token through `ath`. It is not client authentication and does not prevent a compromised host from using its key ([RFC 9449 §§4–7, 11](https://www.rfc-editor.org/rfc/rfc9449.html#section-4)). Proposed deployment policy: permit ES256 proofs, require a 60-second freshness window, AS and resource-specific server nonces, authorization-code `dpop_jkt` binding, and durable `(key thumbprint, proof jti, verifier domain)` replay uniqueness across processes/restarts. Persist only public thumbprints and nonce/proof digests, never private keys or raw proofs. Retain replay entries for at least the accepted freshness/skew interval. Confirm the pinned provider's replay storage and nonce behavior with real integration tests; advertised algorithms alone do not pass the gate.

### Atomic issuance and refresh

Consent completion atomically consumes the exact receipt, records `AdminDelegationGranted`, binds a fresh provider grant/family and emits the audit. Mark activation complete before permitting a code to be exchanged; unfinished/retried orchestration never produces a usable token. Account creation works without workspaces. Server-side lifecycle operations cannot create an unconsented grant.

For initial exchange and every refresh, use one request-scoped PostgreSQL transaction for provider code/refresh consume, family state, authority lifecycle decision/audit and new token artifacts. Refactor the adapter's present independently opened transactions (`services/mcp-auth/src/postgres-adapter.js:35`, `:156`, `:186`) into a transaction-aware adapter for admin token processing; the authority binding must use the same database transaction, not a second generated-handler pool. Do not send a token response before commit. Implement this behind a narrow trusted lifecycle interface calling shared reducers; it is not a public mint API. If the provider integration cannot support this atomic unit, stop the build lane and revise this design before release; do not substitute best-effort callbacks.

Lock order for every admin operation/revoke/token lifecycle: owner/account, root-to-leaf admin grants in deterministic order, provider families in deterministic order, affected workspace streams, then rate/credential rows. Move family lock acquisition out of lower-level paths that would invert this order. Unauthenticated provider lookups may identify a candidate internally, but repeat all checks under locks before consume/write/response. Check live grant/current rights, exact client/resource/key, tombstone, absolute deadlines and scope narrowing. For partial lost rights, refuse refresh and request narrower fresh human consent; do not silently change the consent manifest. Explicit refresh scope may narrow the token, never expand it. Rotation cannot reset creation or successor budgets.

Initial exchange records one `AdminCredentialIssued` and audit; refresh records one `AdminCredentialRotated` and audit in the same transaction as successor persistence. Keep the provider's family tombstone and compare-and-set consume semantics. A concurrent refresh winner produces one successor; a consume loser returns `invalid_grant` and does not revoke the winner merely for losing the race. A subsequent replay of a consumed refresh token terminally tombstones the family, records replay and revokes the linked admin grant/descendants atomically. This extends today's OAuth replay event into the authority model; it must be tested rather than assumed.

Do not persist token-response plaintext in idempotency results. After response loss, the client cannot recover a secret through a management read or retry of a consumed code/refresh token. Fail closed; use `/app` to revoke the uncertain family and begin new consent. A token may have been delivered before transport loss, so describe the state as unknown until durable reconciliation. Issue audit means committed issuance, not proof that a client stored a token. Token responses, nonce retries and failure logs must be redacted.

### Revocation, expiry and operations audit

`/app` human revoke performs the existing account revoke decision **plus insertion of all linked family tombstones in the same database commit**, appending audit before acknowledging success. Refactor adapter `revokeByGrantId` into a reusable transaction helper; never rely on an HTTP call from edge to OAuth or a delayed revocation queue. Status resolution and every admin operation check tombstones/live grant inside their own transaction. Cache JWKS, never positive grant authority. OAuth refresh/mint refuses immediately after revoke commit; access JWT signature validity alone is insufficient.

Revocation SLA means zero additional authorized transactions starting after the revoke commit, not instant cancellation of requests already committed. A concurrent action that acquires locks and commits first remains valid history; revoke first prevents it. Reads also lock/recheck before snapshotting and audit. Queued commands revalidate at execution. If the database/status/audit store is unavailable, refuse operations/token issuance/revoke-success acknowledgement. UI presents unknown outcomes with stable retry IDs and readback.

Suspension, expiry, replacement, replay and client-verification withdrawal fence refresh/access likewise. Replacement ends the prior grant and tombstones its family atomically, preserves its history/budgets, and creates a new consent-bound family. Default deadlines are consent activation time plus thirty days; initial issuance delay never adds time. Expiry enforcement uses database time on every call even if a materializing expiry job has not run. Revocation cascades through admin ancestors and provisioned workers; narrowing/withdrawal intersects descendants rather than deleting ancestry.

Every authenticated admin operation, including reads, refusal, protected-action attempt, surrender, delegation and failed transaction recovery, records human owner, admin principal and grant. Known valid-but-revoked tokens still attribute audit to the verified bound grant before refusal. Completely invalid/unknown credentials go to a bounded security audit without trusting their claimed owner. Audit failure blocks a success response; mutation/domain/audit commit together, and rollback failure auditing uses the existing separate transaction pattern (`supabase/functions/command/index.ts:13207`; `supabase/functions/command/admin-delegation.ts:448`). Keep append-only triggers and least privilege; a privileged database administrator remains a residual tampering risk. Export periodic signed audit digests to independent retained storage as a separately reviewed operational follow-up, not a claimed current safeguard.

### Explicit may-delegate extension

Current code requires the human owner for `grant_admin_delegation` (`src/protocol/admin-authority.ts:185`) and the contract prohibits further admin grants (`docs/design/2026-10-01-AGENT-ADMIN-GRANT-CONTRACT.md:185`). Preserve those checks for all existing scopes. The supplied task permits considering delegation only with explicit “may delegate”; implementing that exception requires Tom's approval of a narrow canonical-contract amendment. Until approved/released, no delegation scope is advertised or selectable.

Proposed exception: a new `admin_delegate_grant` command, enabled only by a separately confirmed `admin:delegate` scope and finite human-approved policy, creates a **pending** child request for one named verified recipient connection/client. It cannot return credentials or impersonate a recipient. The recipient completes hosted OAuth authorization to bind its own DPoP key and receive its normal token response. The original human's consent explicitly authorizes those named recipients and child ceilings; unnamed recipients require new human consent.

Allow depth one only and an explicit child-count limit (default zero; if enabled, default one, maximum three for this initial extension). Child is granular, cannot carry `admin:delegate`, and intersects parent's scopes, selected workspaces, current human rights, targets, worker ceilings, remaining issuance/renewal budgets and expiry. Its deadline never exceeds the parent's. Charge the root's durable aggregate budgets so splitting children cannot multiply quota. No owned-and-future wildcard in a child. Record parent/root/recipient in consent, family binding and audit; show children and dependency in `/app`. Parent revoke/suspension/expiry or loss of delegation authorization fences every child and worker descendant on the next call. Parent renewal never renews or detaches a child. A recipient's own human-origin grant is a new independent consent lineage, never conversion of an existing dependent child.

## /app changes

Extend the existing Admin access/history views with verified publisher and client ID, connection, grant mode, plain permission groups, exact expiry/deadline, OAuth family state, renewal need, last use, effective workspace coverage, worker dependencies and optional child grants. Keep the offline durable indicator. Show active/suspended/expired/revoked/issuance-uncertain states truthfully; an active grant without a completed issuance is not a connected usable client.

“Renew access” starts fresh hosted consent for the same verified client/resource with previous options as an editable proposal, never silent approval. Show scope/workspace/recipient/budget/version changes side by side; widening needs explicit selection and summary confirmation. Expired/revoked scope sets are not copied as authority. After completion display the replacement relationship and descendants that stopped. A human must separately authorize any new child/worker lineage; renewal does not revive tombstones.

“Revoke” uses the existing human account command, including atomic family fencing. Show “Revoked” only after accepted commit, even if a subsequent refresh fails; otherwise show “Result unknown—refresh or retry this request.” Account revoke remains usable without a workspace or agent host. Account/workspace history includes safe owner/principal/grant/provider-family provenance and linked events, never tokens, proof JWTs or private session bindings. Workspace viewers see only permitted relevant actions; another account's grant/family identifiers must not leak through pagination/errors.

## Threat model

Assets: human account authority; OAuth authorization code/access/refresh artifacts and DPoP key; consent manifest; current workspace rights; parent/child grant lineage; issuance quotas; immutable action evidence. Trust boundaries: browser↔AS, metadata publisher↔AS, AS↔PostgreSQL authority, agent host↔admin edge, admin edge↔workspace reducer, `/app` human session↔revocation, operator↔audit storage. Client input, model prompts and client names are untrusted.

| Threat / STRIDE | Required mitigation and proving control | Residual risk |
| --- | --- | --- |
| Consent phishing / S, E | Verified-client admin allowlist; prominent canonical CIMD/DCR identity and redirect host; no metadata-supplied verified badge; explicit full-account second confirmation, expiry/coverage/worker exposure warning; fresh session + CSRF + exact manifest receipt. Test forged familiar name/unverified client refusal alongside verified granular consent success. | A person may approve a malicious verified publisher or overlook the warning; verification cannot establish future host behavior. |
| Token theft on agent host / I, E | Mandatory DPoP access and refresh binding, five-minute access, thirty-day non-sliding deadline, protected runtime store, audience separation, no tool-text secrets; missing/wrong key rejected beside valid-key success. | Compromise of both token store and signing-key execution lets an attacker act within the grant until revoked; DPoP does not constrain an authorized malicious model's intent. |
| Cross-workspace confused deputy / S, E | Verify all family/grant/owner/client/key/connection bindings; intersect token scopes, exact manifest, current roles, selected/shared/future-owned spaces and target/recipient rules inside transaction.
