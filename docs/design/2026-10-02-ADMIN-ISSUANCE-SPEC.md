# Hosted OAuth admin issuance: specification and threat model

Status: design only, 2026-10-02. Option A is the supplied HezLead decision under Tom's authorization. This document proposes implementation requirements; it does not claim issuance, tests, migrations, or releases have happened. Source baseline: `cb15e1ae226544798c8c918a35d990a626109938` (`origin/main` at preparation). All file:line references below refer to that baseline, not future line numbers.

## Decision and boundaries

Issue the first admin credential through the hosted OAuth consent service. Use a distinct **admin grant class** with separate consent, resource, scope set, provider grant, refresh family, and connection identity. On the OAuth wire, retain the standard `authorization_code` and `refresh_token` grant types; “admin grant type” means this separate authority class, not a new client-facing mint or nonstandard `grant_type`. No existing MCP consent implicitly authorizes admin access.

The only admin credentials after cutover are OAuth-issued ES256 access JWTs and the provider's rotating opaque refresh tokens. Delivery is the normal HTTPS OAuth token response to the MCP client's credential store. Retire `handleAdminRuntimeCommand`, its runtime-proof actor, `swm_adm_`/`swm_adr_` issuance and validation, and its private admin delivery callback. Reuse its bounded pinned-issuer/JWKS verification primitives for verifying the OAuth access JWT, with the new claims and DPoP checks below. A signed OAuth access JWT authorizes routine commands directly; it cannot authorize another mint through the old proof route.

**Hard activation gate:** proposed `admin_issuance_enabled` defaults false and must stay false through lanes 3–4 until lane 5 has landed and its legacy-unreachable test passes. Both authorization and `/token`, including refresh, enforce it; `getResourceServerInfo` must reject the admin resource while closed. A consent-page flag alone is insufficient. Activation additionally requires a durable cutover marker written only after legacy rows are terminally fenced, exact reviewed live lane-5 revision/readback, and the lane-8 complete-chain proof. Missing configuration, marker, revision or proof fails closed. Neither an enabled flag with an old edge nor a new AS with an old opaque credential path may issue admin tokens. Closing issuance later does not replace revocation of existing grants.

Make that predicate executable: M3 `admin_cutover_state` records terminal `legacy_closed`, approved lane-5 edge SHA/auth-contract version and lane-8 evidence digest, writable only by the reviewed release role. Fixed HTTPS endpoint `https://api.commonswarm.com/admin/.well-known/readiness` returns only the running edge's build SHA/auth-contract version and database closure status; it is public deployment metadata, not an authenticated admin tool. Before each admin authorization or code/refresh exchange, the AS requires the enabled flag, complete matching receipt and live readiness matching the configured approved SHA/version. No cached positive readiness; timeout, missing endpoint, old binary, mismatch or incomplete receipt refuses. `getResourceServerInfo` invokes the same check, not a separate UI boolean. Release rollback cannot leave an old edge minting against a stale receipt; its opaque database access is also permanently fenced. Lane-4/8 premature-activation tests exercise all three components with a new-edge positive control.

DPoP is mandatory for **every admin scope, including read-only**. Clients unable to retain a DPoP key and produce proofs cannot request admin grants. They may continue using the ordinary MCP connector. This is a release compatibility gate, not a reason to fall back to bearer admin tokens. The admin connector is a separate MCP resource at `https://api.commonswarm.com/admin`; ordinary coordination remains at `https://mcp.commonswarm.com/mcp`.

Consent explains an incompatible client before offering permissions: “This client cannot prove possession of its access key. Admin access is unavailable. You can use the ordinary MCP connection.” It cannot confirm an admin receipt. Provider DPoP algorithm advertisement or default enablement does not establish this requirement; lane 4 explicitly requires proof/key binding at code exchange and refresh, and lane 5 requires it at every protected request.

The first release defaults to thirty days and permits an earlier positive expiry, with a thirty-day maximum. Only fresh human consent creates a replacement grant and new family. Refresh does not renew the grant or extend its absolute deadline. Full account remains bounded routine administration, with no implicit permission to create further admin grants.

This specification does not implement billing, unsupported routine operations, external provider authorizations, human impersonation, or a CLI issuance verb. Provisioned worker credentials remain a separate credential class. Their existing protected recipient delivery is not a second admin authentication system and must never be presented as the way to issue the first admin credential.

## Consent and authority mapping

The client requests a maximum scope envelope; the person can choose an equal or narrower subset. Render both the client's request and the final human selection from one versioned registry shared with enforcement. Never add a scope the client did not request. Full account is available only when the request permits the complete supported routine bundle. No wildcard OAuth scope and no silent conversion of broad granular choices into full account.

Start in “Choose permissions” mode, with read-only selected and all mutation boxes clear. Offer “Full account” as a distinct radio choice, followed by a second confirmation of the complete summary. Read-only can be used alone or accompanies each mutation group. ### Registry and dormant-permission fencing

Registry-v1 validation requires every scope, including unavailable operations (`src/protocol/admin-policy.ts:108`). Do not issue new OAuth admin grants with that shape. Lane 1 proposes a canonical manifest revision, allocated as registry v2 before issuance, adding sorted, unique `capability_names` (exact command names) and an immutable `availability_digest` alongside `registry_version` and `scope_names`. Include all in `manifest_digest`, the consent receipt, grant projection and provider binding. Full account explicitly selects the complete **available routine** bundle at that version, within the client's requested ceiling; granular selects its subset. Unsupported scopes and commands are disabled in consent and absent from both lists. Old v1 rows/digests remain historical and terminally fenced at cutover; they are never converted or inferred as OAuth consent.

One shared, versioned availability map, keyed by registry version and command, supplies consent rendering, `adminManifestValid`/effective policy in `src/protocol/admin-policy.ts`, `parseAdminRoutineCommand` in `src/protocol/admin-routine.ts`, and admin tool listing/dispatch. The parser refuses an unavailable command before any effect even if the scope exists. Dispatch intersects the consented version's command definitions/capability list with current executable availability from that same map; scope presence alone is insufficient. A current removal immediately restricts use without rewriting the immutable consent snapshot. Adding a scope, adding parser support, or changing a command's authority semantics requires a registry version increment and new consent; changed authority definitions cannot execute under older consent. Missing/unknown versions refuse, never fall back to the newest map. Even an accidental same-version availability addition cannot expand an old explicit capability list. A new command sharing an old scope still fails this test. Lane 1 must prove both cases with old/full and new/fresh-consent controls. This work does not implement the unavailable routine commands.

Require a fresh trusted human authentication (within five minutes), verified Origin, CSRF token, and single-use consent receipt bound to the session and canonical exact manifest. Bind request client ID, redirect URI, resource, PKCE challenge, DPoP key thumbprint, metadata snapshot, scope ceiling, interaction/version, and replacement grant as well. Changed inputs invalidate confirmation. Back/refresh can recover a pending request but cannot confirm twice or substitute a broader manifest. A model acknowledgement or an operator approval flag is not human consent. The current core already checks session-bound, unconsumed, unexpired receipts and explicit full-account selection (`src/protocol/admin-authority.ts:174`, `:185`; `supabase/functions/command/admin-delegation.ts:358`); the extra OAuth bindings are new work.

### Client identity and phishing rules

All admin clients require an active service-owned verification record. HezLead prepares the review; Tom, or a human security approver explicitly appointed by Tom, approves it. An agent cannot approve its own client. Verification records pin canonical `client_id`, exact redirect URI set, application type, publisher identity and independently checked publisher contact, canonical metadata digest/version, allowed admin scopes and separate full-account/delegation eligibility. Store approver, review time, nonsecret evidence references and successful PKCE/DPoP/redirect test results. Verify publisher control of the metadata origin using an independently established contact and an origin-control challenge; inspect redirects, proof-key storage and the consent/code-exchange flow. This is a human-reviewed trust decision, not cryptographic client authentication or a promise of safe future behavior. Do not seed an assumed reviewer client; no record means no admin access.

CIMD hosting alone grants no eligibility. DCR clients are forbidden from admin entirely in v1, even if someone adds a verification row. Pin `features.registration.enabled=false` in the v1 provider configuration; any future ordinary-MCP DCR enablement must preserve the explicit admin prohibition and provenance check. Native applications, loopback redirects (including `localhost`, IPv4/IPv6 loopback) and custom URI schemes are refused for admin unless the exact client/application/redirect set receives explicit exceptional verification. `nativeLoopbackEnabled` for MCP does not confer that exception. Such approval must test code interception with mandatory PKCE S256, authorization-code `dpop_jkt`, same-key exchange/refresh and protected key storage. No generic loopback wildcard. Unverified clients cannot see the full-account option or delegation; verification is also enforced server-side for granular consent. Unknown CIMD clients may use ordinary MCP; admin returns `unauthorized_client` with a safe reason.

Display escaped text only; do not fetch remote client logos on consent. Preserve pinned public-HTTPS metadata fetching, body/time bounds and redirect refusal (`services/mcp-auth/src/metadata-fetch.js:234`, `:300`). A metadata digest, redirect, application-type or publisher/contact change immediately marks verification ineligible and fences existing admin grants/families in the same lifecycle transaction; fresh reviewed verification and fresh consent are required, never automatic reactivation. Check the approved snapshot at authorization, consent finish, code exchange and refresh, and active verification/version in every edge authority transaction. An approver may withdraw verification; withdrawal records a reason and atomically suspends/revokes linked grants and tombstones their families. If metadata cannot be checked at authorization/token processing, refuse rather than trust an expired cache. Lane 3 tests changed metadata, withdrawal and re-verification without resurrection.

Full account requires a second CSRF-protected, single-use confirmation tied to the exact summary digest and verification snapshot, distinct from selecting its radio button. Warning: “This client can create workspaces and change seats and invitations within these limits. That includes future workspaces you own. Workers it creates may read workspace messages and files. If the client or agent host is compromised, someone else can use this access until it expires or you revoke it.” Show exact capabilities, limits, expiry, client/redirect host and excluded permissions. Edited metadata or summary invalidates the second confirmation. Verification reduces impersonation; a verified malicious publisher remains a residual risk.

## OAuth and resource API

Use issuer `https://mcp.commonswarm.com`, its existing authorization/token endpoints and pinned JWKS, with an explicit resource allowlist. Requests must contain exactly one resource at authorization, code exchange and refresh. Accept `https://api.commonswarm.com/admin` for the admin class and `https://mcp.commonswarm.com/mcp` for the ordinary class; reject arrays, aliases, trailing-slash variations and missing resources. Never allow a single provider grant or refresh family to cover both. A client using both resources gets two independent consents, connection IDs and stores.

### Single-resource provider grants

Add a durable `provider_grant_resources` binding for **both** classes, primary key `provider_grant_id`, with immutable exact resource, owner, client, connection and grant class. Enforce disjoint hosted/admin links; one provider grant ID cannot appear in both. Every code/access/refresh artifact refers to that binding; adapter upserts validate resource/class and refuse mismatches, including a provider Grant payload whose resource-scope map contains another audience. Backfill existing MCP grants only from verified hosted bindings as MCP; missing/ambiguous rows fail closed. A provider session's previous MCP grant is never evidence of admin consent.

Required service changes:

- `services/mcp-auth/src/interactions.js`, `createInteractionHandler` → returned `handleInteraction`, consent finish (`:389`–`:409`, `:451`–`:454`): branch by the validated single resource **before** hosted workspace selection/consume. Admin uses the admin receipt and fresh Grant; retry may `Grant.find` only the same pending admin binding after checking owner/client/resource/class. Never reuse an MCP Grant, add admin resource scopes to it, or call the hosted activation path for admin. MCP retries likewise check MCP binding. Fresh admin consent cannot silently upgrade or merge the session's Grant.
- `services/mcp-auth/src/provider.js`, `createMcpProvider` → `features.resourceIndicators.getResourceServerInfo` (`:100`), `defaultResource`/`useGrantedResource`, `extraTokenClaims` (`:150`): closed gate rejects admin at authorization and token endpoints; opened gate selects exact audience/scopes only after verified-client and bound-class checks. Token claims/status derive from the durable class-specific binding, never from requested `resource` alone. Code and refresh must match their original resource, client, key and class; public-client metadata must explicitly require DPoP for admin. Discovery enablement alone is insufficient.
- `services/mcp-auth/src/server.js`, `startServer` → `clientMetadataAccepted` (`:186`): preserve ordinary MCP metadata validation/cache; return/use admin eligibility only from the active pinned verification record, with explicit DCR/native rules. Because this callback currently receives metadata without a request resource, it must not be the sole resource authorization check: wire the same eligibility service into `getResourceServerInfo`, admin consent finish and token processing. `providerGrantActive` (`:177`) resolves the bound class and uses the current transaction's client for admin status.

Lane-4 `mcp-refresh-never-admin` obtains a real MCP code/refresh family, requests admin at refresh and subsequent consent with that same provider Grant, and attempts adapter multi-resource upsert. Each fails without admin artifacts/audit; ordinary MCP refresh still succeeds and separately confirmed verified admin consent succeeds with a different family/connection. Lane 8 blocks activation until this passes on the exact combined build.

Admin resource scopes are the granted existing registry strings, optionally `admin:delegate` only after its extension. `openid`/`offline_access` retain their protocol meaning; `mcp` is refused for an admin resource and admin scopes are refused for the ordinary resource. `offline_access` requests the rotating refresh token; without it access still cannot exceed the same consent deadline. Publish exact supported scopes and protected-resource metadata at the admin resource's discovery path, naming the same issuer. An ID token never authorizes an admin operation.

Return `access_token`, `token_type=DPoP`, actual clipped `expires_in`, exact granted `scope`, and rotating `refresh_token` when requested. Optional nonsecret response metadata includes `admin_grant_id`, `connection_id` and absolute `grant_expires_at`. Set no-store headers. Tokens go only to the OAuth client/runtime credential store, never a model tool result, transcript, URL, redirect fragment, audit, event or report. The authorization redirect carries only the standard short-lived code/state; the token endpoint consumes code plus PKCE and a proof from the bound key.

DPoP is proof of a bound key, not client authentication or protection against a compromised signing host. Resource proofs bind method/URI and access token; code exchange binds `dpop_jkt`, and refresh keeps the same key. Key changes require fresh consent and a replacement family. The wire checks below follow [RFC 9449 §§4, 6–10](https://www.rfc-editor.org/rfc/rfc9449.html#section-4); freshness, storage and nonce lifetimes are this deployment's policy.

### Edge admission and MCP client use

Add an admin MCP edge entry point and route public `https://api.commonswarm.com/admin` to it, preserving that public URL for DPoP URI verification through trusted ingress configuration. Add the route to `deploy/edge-runtime/main/router.ts` and the relevant edge type-check/build lists; the current function allowlist contains only command/read/capability/activity/h0/mcp (`deploy/edge-runtime/main/router.ts:1`). Match public `htu` without trusting caller-supplied forwarded-host headers. No alternate unreviewed alias may bypass proof URI checks.

### Resource-server DPoP verification

Both admin MCP and the admin branch of `/functions/v1/command` use one common verifier, with no Bearer compatibility switch. Parse exactly one `Authorization: DPoP <access-jwt>` (scheme case-insensitive) and one `DPoP` proof header; refuse duplicates, comma-joined values and malformed/bounded-overflow inputs. Admin JWT as `Bearer` is refused even with a valid proof. First verify every access-token field above, including required `grant_class=delegated_admin` and `cnf.jkt`; do not reuse the legacy verifier's UUID interpretation of `grant_id` or its signature-only admission.

Verify proof signature with its embedded **public** P-256 JWK, `typ=dpop+jwt`, `alg=ES256`, with no private material, remote key URLs or unsupported critical headers. Require actual `htm`, exact configured public `htu` path/origin without query/fragment, integer `iat`, bounded nonempty `jti`, `ath` hash of the presented token and matching key thumbprint in `cnf.jkt`. Refuse missing/mismatched fields. URI comparisons use reviewed normalization rules, never request-controlled forwarded headers. The command branch uses its own configured public URI, not the admin MCP URI. [RFC 9449 §4.3](https://www.rfc-editor.org/rfc/rfc9449.html#section-4.3).

Use PostgreSQL time for `now-60s <= iat <= now+5s`; no token/grant-expiry grace. Require an admin-resource nonce, separately from the AS nonce. Proposed `dpop_nonces` stores SHA-256 nonce digest, `jkt`, verifier domain, issued time and 60-second expiry; generate unpredictable 256-bit values, allow bounded concurrent valid nonces, never overwrite one client's nonce on another request. Nonces may be reused while valid only with fresh proofs. Missing/expired/wrong nonce returns resource HTTP 401, `WWW-Authenticate: DPoP error="use_dpop_nonce"` and `DPoP-Nonce`; AS uses HTTP 400 with the OAuth error. Challenge after valid signature/key checks, without grant mutation or code/refresh consumption. Retry uses a new proof/jti and the same command ID. Apply rate/body/time limits; expose the nonce response header to permitted browser clients and redact it in evidence. [RFC 9449 §§8–9](https://www.rfc-editor.org/rfc/rfc9449.html#section-8).

**Durable shared replay store:** M2 creates `commonswarm_oauth.dpop_proof_replays(jti, jkt, verifier_domain, accepted_at, expires_at)`. `jti` is the bounded public proof identifier (1–200 bytes), `jkt` the public thumbprint; primary key/unique constraint **`(jti, jkt)`** spans AS and both resource entry points. Domain is retained for diagnostics, not a way to evade uniqueness. After cryptographic/binding/nonce checks, atomically `INSERT ... ON CONFLICT DO NOTHING RETURNING ...`; no returned row means replay and refusal. Commit replay admission before authority dispatch, even if dispatch later rolls back. Proofs are one-use, while a fresh-proof retry can recover an idempotent command result. Retain entries five minutes from database acceptance, exceeding the entire 65-second freshness/skew window; an indexed, bounded maintenance job deletes only expired rows. ### Atomic issuance and refresh

**Chosen design: shared PostgreSQL transactions, no asynchronous issuance outbox.** Lane 4 first proves a transaction integration spike against pinned oidc-provider 9.12.2; it may not ship atomicity as an assumption. The present `transaction(pool, callback)` opens/releases its own client (`services/mcp-auth/src/postgres-adapter.js:35`–`:47`), `consume` is an independent conditional query (`:66`–`:89`), and `revokeByGrantId`/`upsert` open transactions (`:156`, `:186`). Wrapping only `extraTokenClaims` or calling an edge handler after provider save does not satisfy the design.

At AS request ingress, a trusted admin transaction coordinator identifies the candidate interaction/code/refresh and bound class by read-only lookup, then acquires **one** `pg` client, begins a transaction, locks in the order below and re-reads the candidate. Requested resource cannot relabel an MCP artifact. A Node `AsyncLocalStorage` request context carries that exact client and verified lifecycle capability through the admin branch of `handleInteraction`, the provider callback/resumed authorization and admin token processing. All admin adapter methods (`find`, `findByUid`, `findByUserCode`, `consume`, `upsert`, `destroy`, `revokeByGrantId`) and status/consent helpers use the context client; no nested BEGIN/COMMIT, independently acquired pool client, or fallback autocommit is permitted for a bound admin artifact. Encountering admin state without context refuses. The existing MCP adapter behavior may remain outside this context, with single-resource checks in both branches. A transaction assertion/traced backend PID proves actual adapter calls participate; AsyncLocalStorage alone is not proof.

The authority bridge runs shared pure reducers and narrow PostgreSQL lifecycle functions on that same client, writing account grant/projections, event/audit and provider state in that transaction. Refactor generated management/consent bindings to accept the coordinator's client instead of calling a remote edge or acquiring `postgres.js`'s separate pool. OAuth runtime gains only approved function execution, not general `swarm` mutation. These are trusted internal operations with fresh-human or verified-family provenance, never publicly callable mint functions.

Consent and token processing use distinct request-scoped atomic units; no transaction spans a browser redirect:

1. **Consent finish:** consume the single-use receipt and second confirmation if needed, append `AdminDelegationGranted` and audit, create the admin grant/immutable family binding, persist the provider **Grant artifact** plus completed interaction/continuation state, and mark activation complete in one transaction. Account creation works without workspaces. Buffer any `interactionFinished` response until commit; an incomplete grant cannot authorize the continuation. If the provider creates the authorization code on a later resumed `/authorize` request, that request rechecks the committed receipt/grant under locks, persists the one-time code artifact and its lifecycle audit atomically, then returns the code redirect. It cannot reconstruct or widen consent.
2. **Code exchange or refresh:** after separate committed proof-replay admission, lock/recheck live consented binding; CAS-consume the code/refresh, apply reducer lifecycle/generation/budget decision, persist successor token artifacts, the signed JWT's `admin_access_issuances` record and `AdminCredentialIssued`/`AdminCredentialRotated` plus audit in one transaction. Store only safe JWT JTI/bindings/deadlines in the issuance ledger, never raw access JWT or recoverable token-response plaintext. Signing and all awaited provider adapter saves occur before commit. Token claims/status hooks read the same client. No token artifact or success audit survives rollback alone.

Wrap the entire admin provider/interaction response path with bounded in-memory buffering of status, headers, redirects and body; suppress `writeHead`/`write`/`end`/stream flush until commit. Commit failure or uncertain commit discards the response and reports an unknown outcome; never release staged secrets. Commit only after all provider adapter writes and audit succeed; deferred/unawaited writes are forbidden. Explicit security outcomes such as sequential-refresh replay commit the family tombstone, linked grant revoke and failure audit before the buffered `invalid_grant` response. Other failures roll back the whole issuance unit. Proof admission remains consumed independently, so a retry needs a fresh proof. Error paths must not accidentally roll back a deliberate family fence.

Lane-4 `admin-atomic-provider-transaction` must prove real HTTP consent finish/continuation, code exchange and refresh use one backend transaction per unit; inject receipt-consume, Grant/code/token-save, reducer/audit, signing and commit failures and test concurrent receipts/consumes and response loss. Verify no partial consumed receipt/grant/artifact/success audit, no released response before commit, and replay-fence persistence on an error response. If any pinned provider path escapes the context/response buffer, **stop lane 4 and revise the architecture before activation**. No best-effort callbacks or independently committed “pending” tokens. Lane 8 requires this gate with the combined exact build.

Lock order for every admin operation/revoke/token lifecycle, including verification withdrawal: client-verification/issuer-key policy locks in deterministic order, owners/accounts in deterministic order, root-to-leaf admin grants, provider families, affected workspace streams, then rate/credential rows. Key-denial checks take the same issuer/`kid` policy lock as a denial write even when no deny row exists. Bulk client withdrawal enumerates owners under the verification lock and follows the same order; no callback may acquire verification after owner locks. Move family lock acquisition out of lower-level paths that invert this order. Unauthenticated provider lookups may identify a candidate internally, but repeat all authority checks under locks before consume/write/response. Check live grant/current rights, exact client/resource/key, tombstone, absolute deadlines and scope narrowing. For partial lost rights, refuse refresh and request narrower fresh human consent; do not silently change the consent manifest. Explicit refresh scope may narrow the token, never expand it. Rotation cannot reset creation or successor budgets.

Initial exchange records one `AdminCredentialIssued` and audit; refresh records one `AdminCredentialRotated` and audit in the same transaction as successor persistence. Keep the provider's family tombstone and compare-and-set consume semantics. A concurrent refresh winner produces one successor; a consume loser returns `invalid_grant` and does not revoke the winner merely for losing the race. A subsequent replay of a consumed refresh token terminally tombstones the family, records replay and revokes the linked admin grant/descendants atomically. This extends today's OAuth replay event into the authority model; it must be tested rather than assumed.

Because the new owner/family locks serialize requests, retain the trusted ingress lookup's consume/generation observation to distinguish those outcomes. If ingress saw an unconsumed predecessor but the locked re-read sees it consumed, refuse as a racing loser **before** oidc-provider's consumed-token replay path; do not invoke family revoke. If ingress already saw a consumed predecessor, a valid same-key proof reaches the sequential replay fence. The client cannot choose this classification. Neither path can consume again or issue a successor; test concurrent arrival with a barrier and later replay after winner commit on the real provider. This closes a race introduced by simply wrapping the existing provider flow in broader locks.

Do not persist token-response plaintext in idempotency results. After response loss, the client cannot recover a secret through a management read or retry of a consumed code/refresh token. Fail closed; use `/app` to revoke the uncertain family and begin new consent. A token may have been delivered before transport loss, so describe the state as unknown until durable reconciliation. Issue audit means committed issuance, not proof that a client stored a token. Token responses, nonce retries and failure logs must be redacted.

### Revocation, expiry and operations audit

`/app` human `revoke_admin_delegation` writes the admin grant's terminal state **and every linked OAuth family tombstone in one PostgreSQL transaction**, with account events/audit before success acknowledgement. Refactor adapter `revokeByGrantId` into a reusable helper accepting the caller's transaction; human edge revoke calls the same bounded family-fencing database function on its own transaction client. No HTTP hop, delayed queue or provider-only revoke. Descendant grants/families are fenced in the same authority decision. Lane-4 `admin-revoke-family-atomic` injects failures on both writes to prove all-or-none state; lane-5 `admin-revoke-every-request` proves refused refresh, tool list, metadata read and action immediately after revoke, paired with an active independent grant.

The edge checks durable grant state **and** tombstone, verification/version, exact provider binding, deadlines and ancestors on **every** authenticated admin request, including MCP initialization/tool listing/control-plane reads and idempotent-result delivery. It opens an audited authority transaction even when no workspace mutation occurs. OAuth `providerGrantActive` and `extraTokenClaims` use the admin resolver within the token transaction, not hosted-only status. No positive authority cache; database lookup failure refuses. JWKS public-key caching cannot confer authority: a durable issuer/`kid` deny record is checked on every call and token issuance, allowing compromised-key withdrawal to take effect despite cached keys. Normal planned key rotation retains trusted old keys only for outstanding bounded token lifetimes; emergency withdrawal fences affected families and requires new consent/key material under an incident plan.

Revocation SLA means zero additional authorized transactions starting after revoke commit. A concurrent action that acquires locks and commits first remains valid history; revoke first prevents it. Reads lock/recheck before snapshotting/audit; queued commands revalidate at execution. Only an already-authorized **in-flight** request may finish delivering its committed result, and its execution/response deadline is bounded by the presenting access token's expiry (at most 300 seconds from issuance). Enforce cancellation/output cutoff at that deadline for streaming/long work. The five-minute token TTL is not a post-revoke cache window; completed side effects or data already sent cannot be retracted. If database/status/audit is unavailable, refuse access/issuance/revoke-success acknowledgement. UI presents unknown outcomes with stable retry IDs and readback.

Suspension, expiry, replacement, replay and client-verification withdrawal fence refresh/access likewise. Replacement ends the prior grant and tombstones its family atomically, preserves its history/budgets, and creates a new consent-bound family. Default deadlines are consent activation time plus thirty days; initial issuance delay never adds time. Expiry enforcement uses database time on every call even if a materializing expiry job has not run. Revocation cascades through admin ancestors and provisioned workers; narrowing/withdrawal intersects descendants rather than deleting ancestry.

Every authenticated admin operation, including reads, refusal, protected-action attempt, surrender, delegation and failed transaction recovery, records human owner, admin principal and grant. Known valid-but-revoked tokens still attribute audit to the verified bound grant before refusal. Completely invalid/unknown credentials go to a bounded security audit without trusting their claimed owner. Audit failure blocks a success response; mutation/domain/audit commit together, and rollback failure auditing uses the existing separate transaction pattern (`supabase/functions/command/index.ts:13207`; `supabase/functions/command/admin-delegation.ts:448`). Keep append-only triggers and least privilege; a privileged database administrator remains a residual tampering risk. Export periodic signed audit digests to independent retained storage as a separately reviewed operational follow-up, not a claimed current safeguard.

### Explicit may-delegate extension

Current code requires the human owner for `grant_admin_delegation` (`src/protocol/admin-authority.ts:185`) and the contract prohibits further admin grants (`docs/design/2026-10-01-AGENT-ADMIN-GRANT-CONTRACT.md:185`). Preserve those checks for all existing scopes. The supplied task permits considering delegation only with explicit “may delegate”; implementing that exception requires Tom's approval of a narrow canonical-contract amendment. Until approved/released, no delegation scope is advertised or selectable.

Proposed exception: a new `admin_delegate_grant` command, enabled only by a separately confirmed `admin:delegate` scope and finite human-approved policy, creates a **pending** child request for one named verified recipient connection/client. It cannot return credentials or impersonate a recipient. The recipient completes hosted OAuth authorization to bind its own DPoP key and receive its normal token response. The original human's consent explicitly authorizes those named recipients and child ceilings; unnamed recipients require new human consent.

Allow depth one only and an explicit child-count limit (default zero; if enabled, default one, maximum three for this initial extension). Child is granular, cannot carry `admin:delegate`, and intersects parent's scopes, selected workspaces, current human rights, targets, worker ceilings, remaining issuance/renewal budgets and expiry. Its deadline never exceeds the parent's. Charge the root's durable aggregate budgets so splitting children cannot multiply quota. No owned-and-future wildcard in a child. Record parent/root/recipient in consent, family binding and audit; show children and dependency in `/app`. Parent revoke/suspension/expiry or loss of delegation authorization fences every child and worker descendant on the next call. Parent renewal never renews or detaches a child. A recipient's own human-origin grant is a new independent consent lineage, never conversion of an existing dependent child.
