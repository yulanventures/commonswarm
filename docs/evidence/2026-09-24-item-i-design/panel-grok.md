## 2. Where the binding lives

**(a) Client field.** `profile.json` records the setup host id. Every `--profile` command presents that same id or exits before the network. This stops an honest agent that points `--profile` at another seat and does not replay that seat's id. A determined process of the same OS user reads the 0600 file and passes the id, or rewrites the field. Spec §1 already says a shared OS account is not a security boundary. Cost: one optional profile key, no migration, no edge change, no extra check latency. `readAgentProfile` accepts exactly two key sets (`src/cloud/agent-profile.ts` 146–151), so the new key must be a third accepted set, the same way optional `workspace_name` was added, or every existing profile becomes `profile_invalid`.

**(b) Server fence.** Setup would set `managed_at` and call `acquire_agent_session`, and the read edge would require `x-cswarm-session-*`. That contradicts §8: managed mode is the human command `enable_agent_management`; acquire on an unmanaged principal fails; reads need no proof. `enforceAgentSessionProof` returns success when `managed_at` is null (`supabase/functions/_shared/agent-auth.ts` 233–234). Nothing under `supabase/functions/read/` checks a proof. A managed session lives 120 seconds (`AGENT_SESSION_TTL_MS` in `src/cloud/session-contract.ts`). Every per-turn check would take that transaction's `FOR SHARE` on the principal and the session row. The same OS user can still read the session key under `~/.config/cswarm/sessions/` and send it. So (b) stops a caller who does not have the key, including another machine, and does not stop the machine-local determined agent in the lesson. It also rejects every current unmanaged writer of that principal.

**(c)** Use (a), and leave the execution-session proof where it already is: command mutations of a principal a human has already made managed. Do not attach that proof to `check`. `checkAgentMessages` calls `bindSessionProof` only when `profileSessionContext` returns a row (`src/cloud/agent-check.ts` 161–162); with no host id it sends nothing, and the read edge ignores those headers. The host-session binding is a separate check from the execution-session key.

## 3. Existing seats

Grandfather them. No `bound_host_session_id` means the new check does not run. Binding on first use would make the wandering agent the owner. The owning session re-runs `cswarm setup` with `--host-session-id`; `saveAgentProfile` allows the same principal and rejects a different workspace or principal. `listen start` does not take `--profile` (`src/cli.ts` usage near line 871), so a long-lived listener keeps its credential file and `--session-context` and stays outside this gate.

## 4. The header-drop mutation

That sentence is a meaningful control only for a server check that refuses a present, wrong proof header and allows the call when the header is absent. That is fail-open. On today's `check` it shows nothing: the read edge never refuses, so dropping the header cannot remove a refusal. A sufficient control is three results in one run: session A with the bound id performs the read; session B, with another id and with the id omitted, exits `profile_host_mismatch` and the fetcher is not called; deleting the comparison in the production function makes B's refusal disappear. The mutation belongs on that comparison, not on the sentence (`docs/org/OPERATING-MODEL.md`).

## 5. Release 1

**Rule.** When setup is given `--host-session-id`, store optional `bound_host_session_id`. When a profile has that field, every `--profile` command presents the same id through `--host-session-id`, or through hook stdin `session_id` for `cswarm hook check` and `check --hook`. Any other presentation, including a missing id, exits `profile_host_mismatch` with `This profile belongs to another session. Stop and tell the operator.` before fetch. No environment read. No `managed_at` change. Unbound profiles stay unbound.

**Code.** Add `requireProfileHost` in `src/cloud/agent-profile.ts`, and call it from `--profile` dispatch in `src/cli.ts` and from `serveMcp` before tools are advertised. Extend the exact key sets in `readAgentProfile` and the write in `saveAgentProfile`. Put one shared next step on `REPAIR_USE_SETUP_FILE` (`src/cloud/agent-connection-token.ts`) and on setup failures: stop and tell the operator; do not open another profile. A checksum failure keeps its own cause. State the rule in `AGENT_QUICK_GUIDE` and in `setupPrompt` (`site/src/components/connect/agent-prompt.ts`). Leave `profile_session_conflict` and `profile_conflict` alone.

**Tests.** Positive: a profile bound to A, checked with A, calls the fetcher. Negative: B, and an omitted id, throw `profile_host_mismatch` and do not call the fetcher. An unbound profile with no id still calls it. Mutation: remove the comparison; B's refusal disappears. Hook stdin A passes; a different stdin id refuses. Production observation after release: setup in session A with A's id; `cswarm check --profile` with B's id is refused with that code; with A's id it reads. The proof-header drop is not this control.

**Left unstopped.** A same-user process that reads or edits the profile and replays the id. Profiles already on disk with no binding. `listen` and any command that authenticates with a credential file rather than `--profile`. A static MCP config that cannot vary `--host-session-id` per session; release 1 does not read `CLAUDE_CODE_SESSION_ID` to fill that in. Writes as another seat that was never bound.
