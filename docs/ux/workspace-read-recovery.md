# Workspace read recovery

Files shows an in-panel Retry after its workspace file-list read fails. The retry performs only that read, disables repeated activation while pending, and applies a result only to the same session, workspace and generation. It does not reload the workspace or retry writes. A successful list is used by the existing Wiki view on its next render; the retry does not rebuild a background editor or discard a draft.

Wiki topic reads have one 15-second budget covering the download grant, fetch and response body. An expired grant cannot start a fetch; owned fetch work is aborted, late results are ignored, and the existing exact-version Retry handles the timeout. The shared command deadline and authentication behavior are unchanged.

Focused real-module tests cover failed then successful retry, duplicate and stale reads, late grant, stalled body and abort, and changed context. The DOM fixture uses the production retry binding and Wiki read owner with the existing Wiki controller and fake transports; it is not a full signed-in app or real server witness. Lead ran the real-owner DOM fixture at 390 and 1440px: both passed the Files busy, duplicate, recovery, focus, draft and stale-context checks and the 15-second Wiki timeout with exact-version Retry; neither viewport overflowed. The site build and six module tests passed. The browser observer was skipped locally under the CI-only browser rule. Independent review remains pending. No real account or server mutation is needed.
